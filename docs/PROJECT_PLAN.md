# 修仙模组系列：项目规划（草案）

更新日期：2026-09-28
状态：阶段 1 修行核心原型开发中；身份、境界、打坐、灵石分级和丹炉循环已接入，仍待游戏内验证和数值调整。

本文把已经确认的方向和仍待讨论的设计分开记录。境界细分、数值、具体身份选项和模块名称都可以在玩法原型验证后调整。

## 项目愿景

逐步制作一系列围绕中国传统修行体验的 Minecraft Java 版模组。每个模组承担清晰的玩法职责，既能单独使用，也能组合游玩；系统成熟后再以任务、配方、配置和兼容内容整合成完整的修行主题整合包。

第一阶段以单人体验为主。架构从一开始按集成服务器负责游戏状态来设计，为之后的多人世界和专用服务器留出空间。联机工具可以负责建立连接，修仙模组本身仍须实现状态同步、存档和服务端判定。

## 已确认方向

- 技术基线为 Minecraft 1.20.1、Forge 47.4.10、Java 17；当前 Gradle Wrapper 为 8.10。
- 先完善单人玩法，核心循环稳定后再系统开发多人支持。
- 第一版只做可玩人类种族；后续可以增加其他种族。
- 玩家开局要选择身份，身份范围包括种族、家族出身，以及宗门弟子或散修等修行背景。
- 开局直接获得基础功法，保证玩家马上可以开始修行；更高阶功法通过游玩逐步获得。
- 修为提升有多种途径，打坐、功法、丹药、资源、探索和历练共同构成成长体验。
- 项目负责人制作和审核美术素材；开发侧按具体需求提供 AI 提示词与技术规格。
- 最终目标是形成相互配合的一系列模组和一套完整整合包，而非只做单一内容模组。
- 世界观方向参考《玄鉴仙族》的“五德、十二炁”框架；游戏中的历史、人物、势力与剧情由本项目原创，具体借鉴边界和体系映射见[世界观设计稿](WORLD_SETTING.md)。

## 核心体验提案

目标循环：

1. 选择角色种族与出身背景。
2. 获得入门功法，学习基本修炼方式。
3. 通过打坐、丹药、资源和历练等方式积累修为。
4. 满足条件后突破境界，并逐步接触更高阶区域、功法与内容。
5. 用新能力探索世界、解决挑战，获得下一阶段的资源与机缘。

丹药是重要的成长助力，但长期设计应让多种途径都有价值。丹药使用上限、药性、根基影响和失败代价尚未定案，应通过原型后再决定。

## 身份与修行数据

建议把身份拆成互相独立的数据维度，避免种族、出身和当前修行关系混成一个不可扩展的选项列表：

| 维度 | 第一版范围 | 后续扩展方向 |
| --- | --- | --- |
| 种族 | 人类 | 妖族、灵族等，具体种族待定 |
| 家族出身 | 凡俗家族、修行世家、没落家族 | 后续增加地区、家族传承和起始资源差异 |
| 修行身份 | 宗门弟子、散修 | 后续增加师承、组织关系和任务差异 |
| 已学功法 | 保证获得一本入门功法 | 通过师承、任务、秘境、探索或交换获得更多功法 |

首版家族和修行身份会对灵根、根骨、悟性、气运的随机分布加权；这些属性会影响吐纳效率、承伤减免和突破消耗。后续再增加起始资源、任务和关系差异，避免背景只改变文本。

玩家数据至少需要能表达身份、境界、修为、已学功法、四项资质和必要的修炼状态。持久化格式包含版本号，为后续属性与境界调整留出迁移空间。

## 境界与成长途径

境界参考《玄鉴仙族》的体系顺序：

**胎息 → 炼气 → 筑基（道人）→ 紫府（真人）→ 金丹（真君）→ 道胎（仙君）**

当前按可查到的资料将胎息设为六轮；其余境界的细分层数、突破材料、失败规则和寿元变化仍需逐项核实后确定。高于道胎的境界暂不加入原型。

计划纳入的成长途径：

- 打坐运转当前功法，稳定积累修为。
- 服用丹药，在合适时机加快成长或辅助突破。
- 探索采集灵植、灵矿和其他天材地宝。
- 通过战斗、委托、秘境和剧情历练取得资源与机缘。
- 后续加入灵脉、洞府、宗门师承等影响长期成长的系统。

功法定义修炼方式和长期成长特性；术法、剑诀等战斗手段单独表达。两者可以关联，但不应让玩家学会一门功法就自动等于获得所有战斗技能。

### 功法评级与突破演出

功法参悟难度只表示读懂并掌握它有多难，不代表吐纳收益高低。难度为 0–10：除入门功法固定 98% 外，基础成功率每级降低 8 个百分点；悟性每 5 点、气运每 10 点各提高 1 个百分点，当前境界层数再提供少量补正，成功率限制在 10%–98%。参悟时长为 5 秒起，每级增加 4 秒。

吐纳效率独立于参悟评级。每本功法有自己的基础速率和契合资质；实际每秒收益按“基础毫点 ×（80% + 契合资质 / 2，最高 130%）+ 气运 / 4 毫点”计算。这样资质与功法相合时会更顺畅，基础功法仍可修行，而高阶典籍有更高基础上限但更难习得。档案页会显示当前功法的实际速率及四项资质的作用。

每次突破都会明确区分小境界与大境界，并使用不同声光演出。当前大境界突破只做仪式表现；雷劫、妖物阻道、道劫等后续应做成可扩展的试炼流程，再逐项确定准备条件、失败后果和境界专属意象，避免把伤害或存档惩罚提前随机施加给玩家。

## 功法阶位与术法门槛

功法有适修下限和境界上限两项规则。参悟、切换运转和突破均由服务端校验；突破目标超过当前功法上限时，玩家需要取得并参悟下一阶功法。当前十二本功法按成长阶段分层，作为首批原创功法内容：

| 功法 | 适修范围 |
| --- | --- |
| 吐纳引气诀 | 胎息 |
| 澄源返照篇 | 胎息至炼气 |
| 无为听息章、抱一守中诀 | 炼气至筑基 |
| 谷神养息篇、上善若水篇 | 筑基至紫府 |
| 复归于婴诀、玄牝门观篇 | 紫府至金丹 |
| 少私寡欲录、知雄守雌篇、知止不殆篇、见素抱朴章 | 金丹至道胎 |

术法系统落地时，每种术法都要声明最低修为境界、所需功法阶位和功法契合条件；服务端在学习与施放时分别验证。功法不仅提供数值效率，也决定角色能触及的术法层次。境界名称与五德、十二炁作为本项目的体系锚点，功法阐释、剧情、术法招式和具体文本保持原创，并在扩展时逐项核对设定来源和引用范围。

## 后续内容路线

- 战斗音乐按遭遇、精英、首领和劫境拆分为可替换音轨，加入音量配置、淡入淡出与战斗状态触发。
- 独特建筑以结构模板和战利品表驱动，先做散修洞府与宗门遗址，再增加区域性生成条件和专属资源。
- 怪物按境界段划分招式、抗性、掉落与生成生态；加入独特模型前先完成可复用的实体属性、战斗音效和战利品接口。
- 美术资源按 16×16 方块贴图、32×32 物品图标和透明 PNG 角色/生物纹理验收；原图留在用户素材目录，模组只打包优化后的游戏尺寸文件。

## 模组边界提案

初期先维持一个 GitHub 仓库，当前 `xiuxian` 工程作为修行核心的起点。用代码包和数据 ID 保持内部边界清楚；当第二个玩法模块形成稳定、可独立启用的内容边界后，再将其加入 Gradle 多项目并输出独立模组 JAR。避免在还没有实际内容时先搭建复杂的多模组工程。

后续候选模块如下，名称和拆分方式仍待验证：

| 候选模块 | 主要职责 | 与核心的关系 |
| --- | --- | --- |
| 修行核心（当前 `xiuxian`） | 角色身份、玩家修行数据、境界、基础修炼流程、功法数据接口 | 基础依赖，保持轻量和服务端权威 |
| 丹道与灵材 | 灵植、采集、炼丹、丹方、丹药内容 | 依赖核心的修为和身份接口 |
| 功法与道法内容 | 更多修炼功法、术法、剑诀及流派内容 | 核心提供数据模型，扩展模组提供内容 |
| 法宝与符阵 | 法器、法宝、符箓、阵法及相关制作玩法 | 与战斗和资源系统通过稳定接口交互 |
| 修行世界 | 灵脉、秘境、宗门、妖兽和高阶区域 | 逐步提供探索与成长目标 |
| 兼容与整合内容 | 其他模组联动、整合包配方、任务和进度配置 | 可选依赖，不反向污染核心 |

整合包不是单一模组。核心玩法稳定后，可以另建整合包配置仓库，或在仓库中设独立 pack 目录；最终方式根据分发平台和协作方式确定。

## 技术原则

- 单人世界也采用服务端权威状态：修为增减、丹药结果和突破校验由服务端执行，客户端负责输入与展示。
- 玩家长期进度序列化保存，并预留数据版本字段，便于存档升级。
- 使用 Forge 网络消息同步界面需要的数据；连接或重进世界后从服务端恢复权威状态。
- 玩家数据可先评估 Forge Capability 方案；具体实现前验证重生、换维度、克隆玩家实体和存档加载行为。
- 种族、背景、功法、丹药和配方优先使用稳定的资源 ID 与数据驱动定义，便于扩展和整合包调整。
- 核心代码区分公共逻辑和客户端代码，避免专用服务器加载客户端类。
- 可选模组缺失时核心仍能运行；跨模组功能放在适配层。
- 需要多人支持时，所有改变状态的操作都由服务端验证，客户端不能自行决定修为或物品结果。

## 开发阶段与完成标准

### 阶段 0：协作基础

准备项目说明、路线图、许可证和忽略规则，建立本地 Git 历史。完成本阶段后，协作者能克隆仓库、按说明构建并提出 PR。

### 阶段 1：修行核心原型

提案范围：人类角色、首批少量背景、开局入门功法、打坐修炼、至少一种基础丹药、一次可体验的境界突破，以及退出重进后保持角色进度。

当前原型已包含：首次进入时通过屏幕中央的身份界面选择家族出身和修行身份；确认前锁定玩家操作；人类角色开局获得吐纳引气诀，未学功法不能打坐；胎息、炼气、筑基、紫府、金丹、道胎境界；快捷键 M 打坐、B 突破、K 打开档案；资质按背景随机并影响吐纳、承伤或突破消耗，初始基础区间已下调至 1–12。境界会反馈到生命、攻击和护甲。丹药使用饮用动作并由服务端结算。四档灵石矿的每区块尝试次数、矿石目标占比、高度与工具等级如下表。四档丹胚需要对应品质灵石与辅料，再用独立配方类型的炼丹炉烧制；丹炉复用原版燃料，但普通熔炉不会处理丹药配方。打坐期间锁定坐姿和位置，环绕粒子、低音量音阶与慢速修为积累已接入。身份界面已加入五德、十二炁背景引子；正式世界历史、美术和背景音乐仍待完善。矿脉概率、配方和境界阈值均为原型参数。

| 灵石品质 | 矿脉高度 | 每区块平均生成尝试 | 矿石目标块占比估算 | 最低镐子 |
| --- | --- | ---: | ---: | --- |
| 下品 | Y=-48 至 24 | 5 条 | 约 89.8% | 石镐 |
| 中品 | Y=-56 至 8 | 0.6 条 | 约 9.0% | 铁镐 |
| 上品 | Y=-56 至 -24 | 0.125 条 | 约 1.1% | 钻石镐 |
| 极品 | Y=-62 至 -48 | 约 0.021 条 | 约 0.1% | 钻石镐 |

比例按 `count × rarity_filter × configured vein size` 估算；区块生成时会受替换地形、空气暴露过滤和随机分布影响，不代表每个区块的实际掉落保证值。

当前尚未完成阶段验收：需要在新世界中验证身份界面、HUD、档案页、打坐、服丹、突破、四档灵石矿生成与挖掘、炼丹炉燃烧与产物、退出重进和死亡重生；丹药曾在用户试玩时引发崩溃，需重点回归检查。多人同步验证和稳定数值也待后续实现。

接下来的开发顺序：先在新世界测试炼丹炉 GUI、燃料与丹胚配方加载、矿脉世界生成、服丹不崩溃和打坐的坐姿/移动锁定/收益，再依据试玩修正成长曲线。之后扩充可采集或种植的灵植、更多丹方和中高阶功法。五德、十二炁仍先作为原创世界观与内容数据的扩展框架，待规则核实后再定义具体道途。

完成标准：玩家能从创建身份开始完成一次闭环；主要状态写入存档；核心流程不依赖额外内容模组。

### 阶段 2：丹道与资源循环

在当前四档灵石矿、丹胚配方和基础炼丹炉上，加入原创灵植、可探索或种植的灵材、按药性区分的丹方与多步骤炼制。让丹药与材料来源、境界进度和探索目标连成循环，再测试丹药成长是否压过其他途径。

### 阶段 3：功法、战斗与器物

扩展功法获取、流派选择和术法战斗；逐步加入法宝、符箓与阵法。每个系统都应为探索或突破带来明确用途。

### 阶段 4：修行世界

扩展灵脉、秘境、妖兽、宗门、师承和高阶区域，为不同境界提供相应的探索内容。

### 阶段 5：整合包体验

串联任务、配方、解锁顺序、难度和兼容配置，让玩家能从凡俗或入门阶段持续成长至高阶阶段。整合包应给出明确的目标节奏，而不是只把模组放在一起。

任务引导优先在整合包配置层制作；可选用 FTB Quests 编排身份选择、入门功法、资源采集、炼丹、境界突破与探索目标。任务数据与兼容配置和整合包一起分发，修行核心不依赖 FTB Quests，单独安装仍可完整游玩。

### 阶段 6：多人与专用服务器

使用两个以上客户端和独立服务端验证玩家隔离、状态同步、重连、死亡/重生、换维度、权限、存档迁移和缺少可选模组时的行为。现有联机模组可以提供连接方式，但不能代替这些验证。

## 美术协作流程

玩法确定后，开发侧为每项素材给出用途、AI 提示词和落地规格，包括尺寸、透明通道、帧序、命名和目标资源路径。项目负责人生成并审核素材，再将正式文件交付到对应 `assets/<modid>/textures/...` 目录。美术风格、原始工程文件是否入库和版权标注方式待进一步约定。

## GitHub 协作提案

- 用一个仓库承载模组系列的规划、核心和后续模块；是否公开或私有待确定。
- 日常开发使用 `feat/`、`fix/`、`docs/` 等主题分支，通过 PR 合并到 `main`。
- Issue 用于讨论功能、缺陷和素材需求；PR 说明玩家可见结果、验证步骤和数据兼容影响。
- 不提交 Gradle 缓存、构建产物、本地世界、密钥或账号令牌。
- 当前工程已连接 `zhaokl123789/xiuxian`，并在开发分支协作；后续继续通过主题分支和 PR 管理改动。

4. 首版背景后续扩展的起始资源、任务、关系和出生地点差异。
5. 五德与十二炁的原作细节核对、模组内映射，以及势力和开场剧情的进一步完善。
6. 后续模组的最终拆分、名称、独立运行规则和版本发布方式。
7. 整合包使用的平台、目标受众、难度与预计游玩时长。
